1. Check the pods came up. There is no PersistentVolumeClaim in this mode - the
   volume is an emptyDir the kubelet creates on the node, so there is nothing to
   bind and nothing to wait for.

   kubectl -n {{ .Release.Namespace }} get pods
{{- else }}
1. Check the claim actually bound. Do this FIRST - a Pending PVC means the pods
   will sit in ContainerCreating and nothing else you try will make sense.

   kubectl -n {{ .Release.Namespace }} get pvc
   kubectl -n {{ .Release.Namespace }} get pods
   kubectl -n {{ .Release.Namespace }} describe pvc | tail -20
{{- end }}

3. Ask it about its volume:

   curl localhost:8080/df       capacity, used, free, and the filesystem type
   curl localhost:8080/boots    how many process starts this volume remembers
   curl localhost:8080/ls       what is on it

   /boots is the one to understand. It reports how many times a process has
   started against this volume:
{{- if eq .Values.storage.mode "none" }}
   with emptyDir the count climbs while the POD lives - the volume is scoped to
   the pod, so a container crash keeps it - and resets to 1 the moment the pod
   itself is replaced. Which, on a real cluster, is constantly.
{{- else if eq .Values.storage.mode "shared" }}
   with a shared volume every replica appends, so distinct_pods_seen grows to
   match your replica count. That is the proof RWX is really working.
{{- else }}
   with per-pod volumes each pod sees only its own line, but that history
   survives a restart - so boots_recorded climbs while distinct_pods_seen
   stays at 1.
{{- end }}

4. Prove persistence (or the lack of it). Delete the POD, not the container -
   a crash restarts the container in place and even an emptyDir survives that,
   so /crash tells you much less than it looks like it does:

   curl localhost:8080/write?mb=32     write a timed 32 MB file, fsynced
   kubectl -n {{ .Release.Namespace }} delete pod -l app.kubernetes.io/name={{ include "demo-app.name" . }}
   # wait for the replacement, re-establish the port-forward, then:
   curl localhost:8080/ls              is the file still there?
   curl localhost:8080/boots           did the boot count survive?

5. Make it scale:

   kubectl -n {{ .Release.Namespace }} get hpa,pods -w
{{- if include "demo-app.isStateful" . }}

   Watch the claims appear alongside the pods - each new replica provisions its
   own disk, which takes longer than starting a container:

   kubectl -n {{ .Release.Namespace }} get pvc -w

{{- if eq .Values.storage.mode "none" }}
6. Do NOT run /fill in this mode. An emptyDir has no filesystem boundary of its
   own - emptyDirSizeLimit is an eviction quota, not a quota the filesystem
   enforces - so filling it fills the NODE disk and takes the other pods on
   that node down with it. Switch to a real volume first:

   helm upgrade --install {{ .Release.Name }} demo -f demo/values.yaml -f demo/values-shared.yaml -n {{ .Release.Namespace }}
{{- else }}
6. Fill it up and watch it break:

   curl "localhost:8080/fill?percent=95"
   kubectl -n {{ .Release.Namespace }} exec {{ if include "demo-app.isStateful" . }}{{ include "demo-app.fullname" . }}-0{{ else }}deploy/{{ include "demo-app.fullname" . }}{{ end }} -- df -h {{ .Values.storage.mountPath }}
   curl localhost:8080/rm?name=fill    clean up afterwards
{{- end }}
